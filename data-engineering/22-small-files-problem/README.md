# 22 · The small files problem

<img src="https://img.shields.io/badge/level-intermediate-B45309?style=flat-square" alt="intermediate"> <img src="https://img.shields.io/badge/video-112s_%2B_35s_short-7C3AED?style=flat-square&logo=youtube&logoColor=white" alt="video 112s + 35s short"> <img src="https://img.shields.io/badge/uses-pyarrow_%C2%B7_duckdb-2563EB?style=flat-square&logo=python&logoColor=white" alt="pyarrow · duckdb"> <img src="https://img.shields.io/badge/topic-data_engineering-0E1525?style=flat-square" alt="data engineering">

**Thousands of tiny files just made this query crawl.** The same 4.4 million click events are written twice: as
5,500 small Parquet files, the way streaming jobs often write them, and then compacted into 4 big files. The same
DuckDB query takes about half a second on the tiny files, where 3.9 MB is spent on file footers alone, and under 50
milliseconds on the big ones. Same data, over 20 times faster, and less than half the size on disk.

## The idea

Every file costs something before any of its data is read. The query engine has to:

1. **Open it** (on cloud storage, that is a network request).
2. **Read its footer**: the Parquet metadata at the end of the file, with the schema, row groups and column
   statistics.
3. **Plan the scan** of that file, then read its few rows.

With 4 files, that cost is paid 4 times. With 5,500 files, it is paid 5,500 times for the same rows. It's like
mailing a thousand envelopes instead of one box: the postage adds up.

The fix is **compaction**: read the many small files and rewrite them as a few large ones. The rows don't change,
only how they are cut into files.

## Run it

You need `pyarrow` and `duckdb` (`pip install pyarrow duckdb`). The script writes the files into folders named
`tiny/` and `big/` next to it, so run it from inside `src/`:

```bash
cd src
python3 smallfiles.py
```

```
tiny: 5,500 files, 45.8 MB
  footers 3.9 MB | query about 0.5 s
big: 4 files, 19.7 MB
  footers 4 KB | query under 50 ms
compacted: over 20x faster
```

It takes about 20 seconds. Nothing in `tiny/` or `big/` is committed: `smallfiles.py` is its own data generator.
Line 5 deletes and recreates both folders, lines 8 to 10 write the 5,500 small files, and lines 14 to 17 write the
4 big ones (about 65 MB of Parquet in total). The lesson's `.gitignore` keeps them out of git, and you can delete them
when you're done.

The file counts, sizes and footer sizes are the same on every run of the same PyArrow version. They shift a little
between versions, because each release encodes Parquet slightly differently: the output above is from PyArrow 18.1
(the version in the video), and PyArrow 25.0 prints `46.1 MB`, `4.1 MB`, `20.1 MB` and `5 KB`. The query times are not
stable at all: they depend on your
machine and on what else it is doing. The script rounds them into wide buckets to keep them steady, but across six
runs here the tiny query landed on "about 0.5 s" or "about 0.75 s", and the last line said 10x, 20x or 30x. The big
query was under 50 ms every time.

The short version (`short/smallfiles.py`, 9 lines) puts the writing into one `write(d, n)` function and builds the
same two folders inside `short/`:

```bash
cd short
python3 smallfiles.py
```

```
tiny: 5,500 files, 45.8 MB
  footers 3.9 MB | query about 0.75 s

  footers 4 KB | query under 50 ms

```

## Files

```
22-small-files-problem/
├── src/
│   ├── smallfiles.py     the code from the video
│   ├── lake.py           the click events, folder reset, the timed DuckDB query, rounded reporting
│   ├── tiny/             generated by smallfiles.py: 5,500 files, not committed
│   └── big/              generated by smallfiles.py: 4 files, not committed
├── short/
│   ├── smallfiles.py     the 9-line version from the short
│   └── lake.py           same as src/lake.py, plus it builds the events and empty folders on import
└── .gitignore            keeps tiny/ and big/ (in src/ and short/) out of git
```

There is no `data/` folder: the click events are built in memory by `clicks()` in `lake.py`, with simple
arithmetic instead of randomness, so every run writes exactly the same files.

## The code

`src/smallfiles.py`, line by line:

| Line | Code | What it does |
|------|------|--------------|
| 1 | `import pyarrow.parquet as pq` | PyArrow's Parquet reader and writer. |
| 2 | `from lake import clicks, reset, query, faster` | The helpers from `lake.py`. |
| 4 | `day = clicks(4_400_000)  # one day of events` | An in-memory Arrow table of 4.4 million rows: `id`, `country`, `amount`. |
| 5 | `reset("tiny", "big")` | Delete both folders if they exist and create them empty. |
| 7 to 8 | `for i in range(5500):` | What streaming jobs often do: one small file per micro-batch. |
| 9 | `part = day.slice(i * 800, 800)` | The next 800 rows. `slice` is a view, it copies nothing. |
| 10 | `pq.write_table(part, f"tiny/{i:04}.parquet")` | Each slice becomes its own file: `tiny/0000.parquet` to `tiny/5499.parquet`. |
| 11 | `slow = query("tiny")  # median of 7 runs` | Time a group-by over the whole folder and print sizes. |
| 13 to 14 | `t = pq.read_table("tiny").combine_chunks()` | Compaction, step 1: read all 5,500 files as one table, and merge its 5,500 chunks into one. |
| 15 to 16 | `for i in range(4): part = t.slice(i * 1_100_000, 1_100_000)` | Step 2: cut it into 4 slices of 1.1 million rows. |
| 17 | `pq.write_table(part, f"big/{i}.parquet")` | Four big files, `big/0.parquet` to `big/3.parquet`. |
| 18 | `fast = query("big")` | The same query on the same rows, now in 4 files. |
| 20 | `faster(slow, fast)` | Divide the two medians and print the speedup, rounded down to a multiple of 10. |

The helpers in `lake.py`:

- `clicks(n)` makes the events: `country` cycles through 10 country codes and `amount` through 500 values from
  0.0 to 49.9, using only the row number.
- `query(d)` adds up the file sizes and the footer sizes (`pq.read_metadata(...).serialized_size`), then runs
  `SELECT country, sum(amount) FROM '<d>/*.parquet' GROUP BY country` in DuckDB. It uses one thread, does 3 warm-up
  runs that don't count, and returns the median CPU time of 7 runs.
- `ms()` and `size()` round the numbers for printing; `faster()` prints the ratio.

The short's `lake.py` is the same, with two extra lines at the end that build `day` and reset the folders when it
is imported. Its `write(d, n)` cuts the 4.4 million rows into `n` equal files, so `write("tiny", 5500)` gives 800
rows per file and `write("big", 4)` gives 1.1 million, exactly like the long version.

## Where the time and bytes go

Each tiny file is about 8.3 KB, and about 0.7 KB of that is its footer: 5,500 footers make the 3.9 MB. Each big
file is about 4.9 MB with a 1 KB footer, and holds its 1.1 million rows in 2 row groups (PyArrow's default cap is
1,048,576 rows per row group).

The tiny folder is also more than twice as big, 45.8 MB against 19.7 MB, for the same rows. Every file restarts
its compression and its column dictionaries (the 10 country codes are stored again in each of the 5,500 files), and
adds its own headers and footer. Big files let the encoding work across many more rows.

## What the video simplified

- **The timing is CPU time, on a local disk, with a warm cache.** After the first runs the operating system keeps
  the files in memory, so the measured gap is the per-file work: opening, parsing footers, planning. On S3 or other
  object storage, every file is also at least one network request, so the gap grows.
- **The compaction here is a full rewrite by hand.** Table formats do it for you, and only for the files that need
  it: `OPTIMIZE` in Delta Lake, `rewrite_data_files` in Apache Iceberg. They also keep readers safe while the files
  are swapped.
- **4 files of 4.9 MB are still small.** The usual advice is files in the hundreds of megabytes, not kilobytes.
  This lesson keeps the data small so it runs in seconds.
- **Too few files has a cost too.** One giant file can't be read in parallel by many workers. Compaction aims for a
  target size, not for one file.

## Try this

1. Change line 8 to `range(550)` and line 9 to `day.slice(i * 8000, 8000)`. How do the tiny folder's size, footer
   total and query time change with 10 times fewer files?
2. Remove `SET threads = 1` from `query()` in `lake.py`. Does the speedup grow or shrink when DuckDB can use all
   your cores?
3. In DuckDB, run `SELECT count(*) FROM 'tiny/*.parquet'` and the same on `big/`. Are the rows really the same?
   Then compare `SELECT * FROM parquet_metadata('big/0.parquet')` with a tiny file.
4. Write the big files with `pq.write_table(part, ..., row_group_size=800)`. The file count stays 4, but how big are
   the footers now, and what happens to the query time?
